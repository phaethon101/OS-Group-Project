## 0. 使用说明（先看这节）

### 0.1 这篇文章是什么

这不是"答案"，而是一份**提示词迭代脚本**。你按 §3 → §6 的顺序，在**同一个对话线程**里依次投喂 V1、V2、V3、V4，每轮记录"提示词原文 → AI 产出 → 暴露的问题 → 修正动作"，最后 V4 通过验证。这个过程本身就是实验报告要交的东西。

### 0.2 操作流程

1. 新建对话，**先把 lab3 工程目录打开**（AI 需要能读到 `kern/trap/`、`kern/driver/`、`libs/`、`tools/` 下的文件），别把整本指导书贴进去。
2. 贴 **V1**，看它产出什么，对照 §3.3 症状表判断错在哪，填进 §8.1 的记录表。
3. 贴 **V2**（伪代码式，故意把两个错误写进去），体会它为什么更糟。
4. 贴 **V3**，观察"边界不清"导致的越界修改。
5. 贴 **V4**（四段式终版），迭代到 §7 全部验证通过。
6. 保存整个对话记录，配合 §8 的段落写进报告。

> ⚠️ 每轮的"AI 实际输出"必须是你真跑出来的。§3.3 / §4.3 / §5.3 给的是**典型症状与判定标准**，用来帮你定位问题，不是让你照抄。

lab3 模块二**无法单独验证**。跑 `make grade` 之前，代码树必须已经具备：

## 1. 写提示词前必须先搞清楚的六件事

不搞清楚这六件事，写出来的提示词要么是"极简指令类"，要么会把错误当规格交出去。

### 1.1 你要填的两个函数，各自只会收到一类事件

`trap_dispatch()` 已经替你分好了类：

```c
static inline void trap_dispatch(struct trapframe *tf) {
    if ((intptr_t)tf->cause < 0) {
        interrupt_handler(tf);   // 最高位为 1 → 中断
    } else {
        exception_handler(tf);   // 最高位为 0 → 异常
    }
}
```

**注意这里藏着一个关键信号**：它用 `(intptr_t)tf->cause < 0` 判断中断，说明中断时 `scause` 的**第 63 位是 1**。这直接决定了下面这一条。

### 1.2 `scause` 的编码：比较前必须屏蔽 bit 63

```
 63                                                        0
+---+-------------------------------------------------------+
| 1 |              中断编号（如 IRQ_S_TIMER = 5）             |   中断
+---+-------------------------------------------------------+
| 0 |              异常编号（如 CAUSE_BREAKPOINT = 3）        |   异常
+---+-------------------------------------------------------+
```

所以时钟中断的 `cause` 实际是 `0x8000000000000005`，**不是** `5`。直接写：

```c
switch (tf->cause) {
case IRQ_S_TIMER:        // 5，永远匹配不上 0x8000000000000005
```

结果就是所有中断都掉进 `default`。这是本模块**最常见、也最先遇到**的 bug。

而且 `tools/test_lab3.c` 里还有一处会把"只取低 8 位"的写法也搞错：

```c
tf.cause = IRQ_S_SOFT | ((uintptr_t)1 << 63);   // 真实的软件中断编码
interrupt_handler(&tf);
tf.cause = 15;                                   // ← 没带 bit63，也调 interrupt_handler
interrupt_handler(&tf);
```

第二种写法要求你在**没有** bit63 的情况下也能正确取出 15。所以正确做法是 `cause & ~(1UL << 63)`，而不是 `cause & 0xff`（虽然这题里两者结果一样，但语义上前者才对）。

### 1.3 `sepc` 的推进量不能写死 4

`sepc` 保存的是**触发异常的那条指令的地址**，`sret` 会把 `sepc` 原样装回 PC。所以异常处理完如果不推进 `sepc`，回去会重新执行同一条指令 → **异常死循环**。

但推进多少？RISC-V 规定：

> 32 位指令的低 2 位**恒为 `0b11`**；否则是 16 位压缩指令。

本项目编译时**没有指定 `-march`**，`riscv64-unknown-elf-gcc` 默认带 C 扩展，于是汇编器会把 `ebreak` 压缩成 `c.ebreak`：

| 指令 | 编码 | 低 2 位 | 长度 |
|---|---|---|---|
| `ebreak`（未压缩） | `0x00100073` | `0b11` | 4 字节 |
| **`c.ebreak`（被压缩）** | `0x00009002` | `0b10` | **2 字节** |
| 测试用非法指令 `.word 0x0000007b` | `0x0000007b` | `0b11` | 4 字节 |

所以写死 `+4` 会让你在 Test 1 里**跳过一条本该执行的指令**（测试随后校验 26 个寄存器，必然对不上）；写死 `+2` 又会让 Test 2 原地死循环。

正确写法是按编码判断：

```c
static size_t instruction_length(uintptr_t epc) {
    uint16_t insn = *(volatile uint16_t *)epc;
    return ((insn & 0x3) == 0x3) ? 4 : 2;
}
```

这正是指导书那句"不同异常对应的指令长度可能不同，不能假定所有异常都使用相同的 epc 偏移量"的落地。

### 1.4 `sbi_set_timer()` 只能设置**一次**时钟事件

OpenSBI 的接口是"到某个时刻触发**一次**"，没有周期性模式。所以每次时钟中断处理完，**必须重新装载下一次**，否则系统只会响一次，`ticks` 永远停在 1。

```c
clock_set_next_event();   // 续下一次，必须在 handler 里做
ticks++;
```

QEMU 上 `rdtime` 频率 10 MHz、`timebase = 100000` → 约 100 Hz，即每 10 ms 一次中断。

### 1.5 框架里**没有** `SHUTDOWN_AFTER` 的定义

我把整棵树 grep 过一遍：`SHUTDOWN_AFTER` **只出现在指导书正文里，代码中不存在**。你必须自己在该文件里定义它。

取值有个坑：Test 3 的观测点是

```c
while (ticks < 200) { asm volatile("" ::: "memory"); }
cprintf("[Test 3] Sustained supervisor timer: PASS (40/40, ticks=%d)\n", (int)ticks);
```

**如果关机发生在 `ticks` 恰好达到 200 的那次中断里，主循环就永远等不到 200**（中断处理期间 `SIE` 被硬件清零，主循环拿不到 CPU）。所以 `SHUTDOWN_AFTER` 必须满足：

```
SHUTDOWN_AFTER * TICK_NUM > 200   →   SHUTDOWN_AFTER >= 3
```

建议取 **10**（10 秒），既满足约束，又不会在 Test 1/2 的 8 秒超时内被打断。

### 1.6 输出是**精确子串匹配**，不是"意思对就行"

`tools/grade.sh` 用 `grep -F` 做固定字符串匹配，少一个字符、多一个 `=` 都算失败：

| 用例 | 必须出现的原文 |
|---|---|
| Test 1 | `Breakpoint at` |
| Test 2 | `Illegal instruction at`、`Supervisor software interrupt`、`Unknown interrupt: cause 15`、`cause    0x00000014` |

其中最后一条 `cause    0x00000014`（**4 个空格**）是框架自带 `print_trapframe()` 的输出格式：

```c
cprintf("  cause    0x%08x\n", tf->cause);
```

`cause = 20 = 0x14`，格式是 `0x%08x` → `0x00000014`。**所以你千万不要去"改进"这个格式**——一旦改成 `0x%016lx`，逻辑正确也判 FAIL。这是本模块最隐蔽的失败点。

## 2. 迭代总览

| 轮次 | 提示词类型 | 核心缺陷 | 触发哪个原则 | 结果 |
|---|---|---|---|---|
| V1 | 极简指令类 | 只说"实现两个 handler"，六条平台事实全缺失 | 任务导向、要求可验证 | `switch` 不匹配、`epc+=4` 错、不续期、`SHUTDOWN_AFTER` 未定义 |
| V2 | 伪代码类 | 把"switch cause"和"epc 加 4"两个错误写进规格 | 任务导向（过细，剥夺 AI 判断） | 错误被固化；AI 越界改 `print_trapframe`、把 handler 写成 `static` |
| V3 | 任务导向但边界不清 | 没列分支清单、没有输出规格、没约束"不要改什么" | 边界清晰、要求可验证 | 漏软件中断、格式自创、`SHUTDOWN_AFTER=2` 掐断测试、改 `ticks` 类型 |

演进逻辑一句话：

> **V1 的失败是"不知道平台事实"，V2 的失败是"我把错误当成了规格"，V3 的失败是"目标对了但没划边界、没给验收标准"，V4 才同时做到任务导向 + 边界清晰 + 要求可验证 + 保留工程语义。**

## 3. 第 1 轮：V1 · 极简指令类（故意做错，用于对比）

### 3.1 提示词原文

```text
帮我实现 lab3 的 interrupt_handler 和 exception_handler。
```

### 3.2 这一轮想验证什么

验证**"信息不足时 AI 一定按教科书套路填空"**。这句话里没有一个字是错的，但它把六个关键决策全留给了 AI 猜：`scause` 怎么编码、指令多长、时钟要不要续期、`SHUTDOWN_AFTER` 取多少、输出什么格式、函数要不要 `static`。

### 3.3 典型产出与症状判定

AI 几乎一定会写出这种"看起来非常标准"的代码：

```c
void interrupt_handler(struct trapframe *tf) {
    switch (tf->cause) {              // ← 错 1
    case IRQ_S_TIMER:
        ticks++;
        if (ticks % TICK_NUM == 0) print_ticks();   // ← 错 2 没续期
        break;
    ...
    }
}

void exception_handler(struct trapframe *tf) {
    switch (tf->cause) {
    case CAUSE_ILLEGAL_INSTRUCTION:
    case CAUSE_BREAKPOINT:
        tf->epc += 4;                 // ← 错 3
        break;
    ...
    }
}
```

逐个症状与判定：

| # | 症状 | 根因 | 现场表现 |
|---|---|---|---|
| 1 | `switch (tf->cause)` 匹配不上 `IRQ_S_TIMER` | 不知道 bit63 是中断标志 | `++ setup timer interrupts` 之后**一行 `100 ticks` 都没有** |
| 2 | 时钟分支里没有 `clock_set_next_event()` | 不知道 `sbi_set_timer()` 是一次性的 | 只打印一次就停，`ticks` 卡在 1，Test 3 等不到 200 |
| 3 | `tf->epc += 4` 一律 4 字节 | 不知道 C 扩展会把 `ebreak` 压成 2 字节 | Test 1 里跳过了 `ebreak` 后面那条 `li`，寄存器校验全崩 |
| 4 | 用了 `SHUTDOWN_AFTER` 但没定义 | 框架里没这个宏 | `make` 直接报 `error: 'SHUTDOWN_AFTER' undeclared` |
| 5 | 输出格式自创（加 `=`、用十六进制） | 没给逐字符规格 | Test 2 的 `grep -F` 匹配失败 |

**判定**：`make` 可能过不了（第 4 条），过了也一定跑不出 `100 ticks`。

### 3.4 迭代决策 → V2

V1 暴露的问题是"AI 在猜"。此时最容易犯的第二个错是：既然它猜不准，我就一步步教它 —— 于是走向 V2 伪代码类。**而这个"教"的过程，恰恰把我自己的理解错误也写了进去。**

## 4. 第 2 轮：V2 · 伪代码类（第二个反例，最危险的一轮）

### 4.1 提示词原文

```text
你按我说的写，不要自己发挥：
1. interrupt_handler 里用 switch 判断 cause
2. case IRQ_S_TIMER: ticks++，然后每 100 次打印 print_ticks()
3. case IRQ_S_SOFT: 打印 Supervisor software interrupt
4. default: 打印 Unknown interrupt 然后 print_trapframe
5. exception_handler 里 case CAUSE_ILLEGAL_INSTRUCTION 和 CAUSE_BREAKPOINT
6. 这两个 case 里打印信息，然后 epc 加 4
7. 其他异常 print_trapframe 兜底
```

### 4.2 这一轮想验证什么

验证一个反直觉的结论：**伪代码式提示词比极简指令更危险。**

因为极简指令下，错误是"AI 猜的"，你还能怀疑它；而伪代码式下，错误是"**我要求的**"，AI 会忠实执行并告诉你"已完成"。第 1 条和第 6 条恰好把 V1 里的错误 1、错误 3 变成了硬性规格。

### 4.3 典型症状判定

| 症状 | 说明 |
|---|---|
| 代码"完全符合要求"但 Test 1、Test 3 全失败 | 因为规格本身就是错的 |
| AI 顺手把 `print_trapframe()` 的 `0x%08x` 改成 `0x%016lx` | 伪代码没划"不许改"的边界，AI 看到 `cause` 是 64 位就"好心"改了，结果 `cause    0x00000014` 匹配失败，逻辑对也判 FAIL |
| AI 给两个 handler 加 `static` | 伪代码没说明"要被外部测试代码 `extern` 调用"，链接报 `undefined reference to 'interrupt_handler'` |
| 你追问"为什么 epc 要加 4"，AI 答不上来 | 它手里只有你的指令，没有体系结构模型 |

**判定**：这一轮最有价值——它证明**约束应当由"行为规格"表达，而不是由"操作步骤"表达**。你要描述"函数返回时必须满足什么"，让 AI 自己去找实现路径，它才有机会纠正你的错误。

### 4.4 迭代决策 → V3

该描述行为了。但只描述行为还不够——还得划"哪些能改、哪些不能改"，否则 AI 会用改框架代码来绕过你的规格。

## 5. 第 3 轮：V3 · 任务导向但边界不清

### 5.1 提示词原文

```text
在 kern/trap/trap.c 里实现 interrupt_handler() 和 exception_handler()，
处理时钟中断、非法指令和断点异常，其他类型用 print_trapframe 兜底。
注意处理好各种边界情况，不要改坏别的东西。
```

### 5.2 这一轮想验证什么

这条已经比 V1/V2 好：**任务导向**做到了（一个完整功能模块）、**保留工程语义**也提到了。但仍踩两个坑：

- **边界不清**："别的东西"指什么？`print_trapframe()` 能改吗？`ticks` 的类型呢？`trap_dispatch()` 呢？
- **要求不可验证**："各种边界情况"无法翻译成具体分支。

### 5.3 典型症状判定

| 症状 | 根因 |
|---|---|
| 漏掉 `IRQ_S_SOFT` 分支 | 测试里它是用**合成 `trapframe`** 直接调用的，不是真实中断，AI 判断"不会发生"就跳过了 → `Supervisor software interrupt` 缺失 |
| `Unknown interrupt: cause = 15 (0xf)` | 自行"美化"格式；grade.sh 是精确子串匹配，多一个 `=` 就失败 |
| `#define SHUTDOWN_AFTER 2` | AI 觉得"跑 2 秒够了"，结果在 `ticks==200` 那次中断里关机，主循环等不到 200，Test 3 FAIL |
| 把 `clock.c` 的 `volatile size_t ticks` 改成 `volatile int ticks` | "不要改坏"被理解成"不要删代码"，约束不住"改类型" |
| 声称"已处理所有边界"但 `epc` 还是 `+4` | 没有可执行的验收标准，AI 无法自查 |

**判定**：失败点非常清晰 —— **"模糊的正确"等于"不可验证"**。必须把每条要求换成能一条条打勾的断言。

### 5.4 迭代决策 → V4

补三样东西，然后就成了四段式：

1. 把任务拆成 Prompt（任务+约束+输出验证要求）/ Rely（最小依赖集+平台事实）/ Guarantee（接口清单+不可改清单）/ Specification（逐分支行为+后置断言）。
2. 把"注意处理边界"换成**七个显式分支 + 12 条能直接对照 `grade.sh` 的后置条件**。
3. 把"不要改坏别的东西"换成一份**逐项列出的不可修改清单**，特别点名 `print_trapframe()` 的格式和 `ticks` 的类型。

## 6. 第 4 轮：V4 · 四段式标准提示词（最终版，直接复制）

> 用 ```` 包裹是为了让你一键复制。整段贴给 AI 即可。

````text
# 任务：实现 riscv64-ucore lab3 的 interrupt_handler() 与 exception_handler()

## 【Prompt｜任务说明】

### 任务详情
在 riscv64-ucore 的 lab3 工程中，实现 `kern/trap/trap.c` 里位于
`//lab3 function2 YOUR CODE` 标记处的两个函数：
`void interrupt_handler(struct trapframe *tf)` 与
`void exception_handler(struct trapframe *tf)`，
补齐 Trap 处理链路的决策层，使内核能够正确处理时钟中断、非法指令异常和断点异常，
并对其他类型兜底。完成后 `make grade` 的三个用例应全部通过。

### 操作约束
- 只允许修改 `kern/trap/trap.c`。改动范围仅限：新增这两个函数、
  可选地新增 `static` 内部辅助函数、补齐必要的 `#include`、以及新增所需的宏定义。
- 必须原样保留 `//lab3 function2 YOUR CODE` 这行注释。
- 两个 handler 必须是**外部链接**（不加 `static`）：`tools/test_lab3.c` 用
  `extern void interrupt_handler(struct trapframe *tf);` 直接调用它们。
- 代码风格与同文件一致（4 空格缩进、`/* * */` 注释块）。
- 必须能在 `-std=gnu99 -Wall -Werror` 下零警告编译通过。
- 不要输出测试代码，不要输出 README，不要改 Makefile。

### 输出验证要求
- 给出可直接替换的完整代码块（两个函数 + 辅助函数 + 必需的宏/头文件）。
- 逐条说明你的实现如何满足下面【Specification】的后置条件 1~12。
- 如果认为某两条约束无法同时满足，先指出冲突再给方案，不要静默取舍。

## 【Rely｜依赖说明】

实现本功能只需要以下文件，不要引入其他材料（尤其不要把整本实验指导书塞进上下文，
冗余信息会干扰你抓重点）：

1. `kern/trap/trap.c` —— 待改文件。重点看 `trap_dispatch()` 如何分派、
   `print_ticks()` 与 `TICK_NUM` 的既有定义、`print_trapframe()` 的输出格式。
2. `kern/trap/trap.h` —— `struct pushregs` / `struct trapframe` 的字段布局。
3. `kern/driver/clock.c`、`clock.h` —— `clock_set_next_event()` 与
   `extern volatile size_t ticks`。
4. `libs/riscv.h` —— `IRQ_S_SOFT`(1) / `IRQ_S_TIMER`(5) / `IRQ_S_EXT`(9)、

## 【Specification｜行为规格】

### 前置状态
- `idt_init()` 已把 `stvec` 指向 `__alltraps`，`sscratch` 已置 0。
- `clock_init()` 已使能 `sie.MIP_STIP` 并装载第一次时钟事件，`ticks == 0`。
- `tf` 指向栈上完整的 `struct trapframe`，`cause` / `epc` 由 `SAVE_ALL` 从 CSR 读出。

### 执行步骤
S1. 在 `interrupt_handler()` 开头，把 `tf->cause` 的最高位屏蔽，得到中断编号 `code`。
    不允许直接用 `tf->cause` 做 `switch`。

S2. 按 `code` 分支：
- **S2a `IRQ_S_TIMER`**，严格按此顺序：
  1. `clock_set_next_event();` —— **先续下一次事件**（漏掉这句系统只响一次）；
  2. `ticks++;`
  3. 当 `ticks % TICK_NUM == 0` 时调用 `print_ticks();`（打印 `100 ticks`）；
  4. 当 `ticks >= SHUTDOWN_AFTER * TICK_NUM` 时调用 `sbi_shutdown();`
     `SHUTDOWN_AFTER` 需自行定义，取值必须使关机时刻**晚于 200 次中断**（建议 10）。
- **S2b `IRQ_S_SOFT`**：打印一行包含 `Supervisor software interrupt` 的提示。
- **S2c `IRQ_S_EXT`**：打印一行包含 `Supervisor external interrupt` 的提示。
- **S2d 其他**：打印 `Unknown interrupt: cause <code>`（十进制），随后
  `print_trapframe(tf);` 兜底。

S3. 在 `exception_handler()` 中按 `tf->cause` 分支（异常时 bit63 为 0，可直接比较）：
- **S3a `CAUSE_ILLEGAL_INSTRUCTION`**：打印包含 `Illegal instruction at` 的一行，
  然后把 `tf->epc` 推进到下一条指令。
- **S3b `CAUSE_BREAKPOINT`**：打印包含 `Breakpoint at` 的一行，然后同样推进。
- **S3c 其他**：只调用 `print_trapframe(tf);` 兜底。

S4. 推进 `epc` 时必须按**实际指令长度**：读取 `tf->epc` 处第一个半字，
    低 2 位为 `0b11` 则 4 字节，否则 2 字节。

### 后置条件（必须同时成立，全部可验证）
1. 两个 handler 均为外部链接（`nm bin/kernel` 里显示为 `T` 而非 `t`）。
2. `-std=gnu99 -Wall -Werror` 下零警告。
3. 收到 `IRQ_S_TIMER` 后 `clock_set_next_event()` 被调用，后续中断能持续到来。
4. 每收到一次时钟中断 `ticks` 恰好加 1。
5. `ticks` 到达 100 的整数倍时，输出恰好一行 `100 ticks`。
6. `ticks` 达到 `SHUTDOWN_AFTER * TICK_NUM` 时关机，且该时刻 **> 200 次中断**。
7. 合成 `cause = IRQ_S_SOFT | (1<<63)` 调用 `interrupt_handler()`，输出包含
   `Supervisor software interrupt`。
8. 合成 `cause = 15` 调用 `interrupt_handler()`，输出包含 `Unknown interrupt: cause 15`。
9. 合成 `cause = 20` 调用 `exception_handler()`，兜底输出包含
   `cause    0x00000014`（4 个空格，由框架 `print_trapframe()` 决定）。
10. 断点异常处理完成后 `tf->epc` 指向 `ebreak` 下一条，推进量等于其实际编码长度。
11. 非法指令异常处理完成后 `tf->epc` 前进 4 字节。
12. 未列出的类型一律走 `print_trapframe()`，不静默返回、不 `panic`。
````

### 8.2 可直接改写的段落：prompt 是怎么写的

> 本模块要填的两个 handler 看似简单（几个 `switch` 分支），但真正的难点不在逻辑而在**平台约定**：
> `scause` 的最高位混在编号里、指令长度受 C 扩展影响、`sbi_set_timer` 只能设置一次、

> 因此我先通读了 `trap.c`、`clock.c` 与 `tools/test_lab3.c`，把这六条事实整理成【Rely】，
> 再用 `grade.sh` 的 sentinel 反推出 12 条后置条件，最后按四段式组织提示词：
> 【Prompt】界定只改 `trap.c` 且要求零警告；【Guarantee】列出必须交付的 2 个接口与 6 类禁改内容；

### 8.3 可直接改写的段落：遇到的 bug 与解决

| bug | 现象 | 根因 | 怎么解决的 |
|---|---|---|---|
| `switch` 不匹配时钟中断 | `100 ticks` 一行不出 | 不知 `scause` bit63 是中断标志 | 在 Rely 写明编码规则，并给出 `trap_dispatch` 的证据 |

### 8.4 本模块与 OS 原理的对应关系（报告"知识点"那节要用）

| 实验里的东西 | OS 原理里的概念 | 关系与差异 |
|---|---|---|
| `scause` 最高位区分中断/异常 | 中断与异常的语义区别 | 原理讲"中断异步、异常同步"；实验把这个区分编码进 bit63，框架用符号位判断。原理不讲"比较前要屏蔽最高位"这个副作用 |
| 时钟中断里续 `clock_set_next_event()` | 定时器 / 时钟节拍 | 原理默认定时器可周期性重复；实验里 SBI 只能设一次，必须每次手动续期。这是"周期计时"抽象的实现代价 |
| `tf->epc` 的推进 | 异常返回地址修正 | 原理一笔带过"恢复 PC"；实验里要按指令编码区分 2/4 字节，否则死循环或跳过指令 |
| default 兜底 `print_trapframe()` | 未知事件的鲁棒性 | 原理很少讲"不认识的异常怎么办"；实验强制兜底，体现"绝不静默失败"的工程原则 |
| `ticks` + `TICK_NUM` | tick 计数 / 时间片度量 | 原理用 tick 度量时间片；实验里只用来打印和关机，尚未驱动调度 |
| `sbi_shutdown()` | 系统关机 | 原理讲关机要同步文件系统等；实验中 S 模式无法直接关机，必须 `ecall` 到 M 模式。体现特权级对内核能力的限制 |
| `IRQ_S_SOFT` | 软件中断 / IPI | 原理讲核间通信靠 IPI；实验里单 hart，只做了类型识别与打印 |

### 8.5 原理上有、本实验没覆盖的点

- **中断嵌套与优先级**：处理期间 `sstatus.SIE` 被硬件清零，全程无嵌套。
- **中断下半部（softirq / tasklet / workqueue）**：所有处理都在中断上下文同步完成。
- **多核与 IPI**：单 hart，`IRQ_S_SOFT` 未被真正使用。
- **系统调用（`ecall`）**：`CAUSE_*_ECALL` 已定义但未实现，那是 lab5。
- **缺页异常与按需分页**：`CAUSE_FAULT_LOAD/STORE` 未处理，属 lab4/lab9。
- **中断上下文的并发安全**：单核且不嵌套，`ticks` 无需原子操作。
- **时钟驱动调度**：未用 tick 触发上下文切换（lab6）。
- **中断延迟与实时性度量**：无响应时间统计。

## 9. 追问应答预案

| AI 的追问 | 你怎么回 |
|---|---|
| 能不能用 `switch (tf->cause)`？ | 不能。中断时它是 `0x8000…0005`，必须 `& ~(1UL<<63)` 后再比较。 |

| 能不能顺便改 `print_trapframe` 的格式？ | **不能**。`grade.sh` 用 `grep -F "cause    0x00000014"` 精确匹配，改了格式逻辑对也判 FAIL。 |
| 两个 handler 要不要 `static`？ | 不能。`tools/test_lab3.c` 用 `extern` 声明后直接调用它们。 |
| 为什么 `ticks` 不能改成 `int`？ | 它是 `clock.h` 里声明的 `extern volatile size_t`，改了会破坏框架对外接口。 |
| 能不能跑 `make grade` 验证？ | 需要先补齐 lab2 的 `page_init`/best-fit 与模块一，否则链接就失败。 |
| `IRQ_S_SOFT` 真的会发生吗？ | 真实运行时不会，但 `test_lab3.c::test_lab3_handler_fallbacks()` 会用合成 `trapframe` 直接调你的 handler，所以必须处理。 |
